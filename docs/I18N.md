# Internationalisation (i18n)

The app ships in **English** (source language) and **Hindi**. Adding another language is a
data task, not a code task: **no component needs to change**.

## Add a language in 3 steps

```bash
npm run i18n:add -- mr "मराठी" "Marathi"        # code, native name, English name
#   RTL language?  add  --dir=rtl     custom Intl/OG locale?  --intl=mr-IN --og=mr_IN
```
1. The command registers the language in `src/i18n/languages.ts` and scaffolds
   `src/i18n/locales/mr/*.json` with every key present and **empty** (empty = shows English).
2. Fill in the JSON values. Check progress and mistakes any time:
   ```bash
   npm run i18n:check            # % translated, broken {{placeholders}}, mismatched <tags>, stray keys
   npm run i18n:check -- --strict   # also fail on any untranslated key (use once a language is "done")
   ```
3. If the script needs different typography, add its code to the `:lang(...)` lists at the bottom of
   `src/index.css` (Devanagari rules for line-height are already there).

That's it: the switcher lists it (in its own script), `<html lang/dir>`, persistence, date formatting,
`og:locale` and lazy loading (each language is a separate chunk, ~55 KB gzipped for Hindi) all pick it up.

## How it works

| Piece | Where |
|---|---|
| Language registry (single source of truth) | `src/i18n/languages.ts` |
| Dictionaries: flat JSON per namespace | `src/i18n/locales/<lang>/<namespace>.json` |
| `index.ts` per language | **generated** by `npm run i18n:sync` – don't edit |
| Engine (interpolation, plurals, fallback) | `src/i18n/translate.ts` |
| React API | `useLanguage()` → `{ language, setLanguage, t, tOr }` |
| Rich text with links/bold | `<Trans>` (`src/components/Trans.tsx`) |
| Form validation messages | `src/i18n/zodResolver.ts` + `locales/*/validation.json` |
| Insurance type/field/option labels | `src/i18n/insuranceText.ts` + `locales/*/insurance.json` |

**Fallback chain:** selected language → its `fallback` (optional) → English → the key itself (dev warning in console).
A missing translation therefore never blanks the UI.

### In components
```tsx
const { t } = useLanguage();
t("nav.home");                                  // type-checked: a typo fails `tsc`
t("auth.attemptsLeft", { count: 2 });           // plural: picks attemptsLeft_one / _other via Intl.PluralRules
<Trans i18nKey="auth.signup.agree" components={{ terms: <Link to="/terms-of-service" /> }} />
//   en: "I agree to the <terms>Terms</terms>"   hi: "मैं <terms>शर्तों</terms> से सहमत हूँ"  (translators may reorder tags)
```
* **Never build sentences by concatenation** (`"Total " + n + " items"`, `"record" + (n>1?"s":"")`).
  Word order and plural rules differ per language. Use `{{params}}`, `_one/_other` keys, or `<Trans>`.
* **Module-scope data** (arrays/config outside components) cannot call hooks. Either store **keys**
  (`labelKey: "nav.x"`, typed as `TranslationKey`) and call `t()` at render, or build the data in a function
  that takes `t` (see `buildFeatures` in `Landing.tsx`).
* **Never translate identifiers** that are stored/sent to the backend (insurance type ids, dropdown
  *values*, support-ticket categories, plan ids). Translate only the label shown to the user
  (see `insuranceText.ts`, `CATEGORY_LABEL` in `HelpSupport.tsx`, `TOPICS` in `RequestCallDialog.tsx`).
* Runtime-only keys (`status.${apiStatus}`): use `tOr(key, fallback)`.
* Outside React (class components, utilities): `translate(getActiveLanguage(), key, params)`.

### Plurals
Define `key_one` and `key_other` (and `_zero/_two/_few/_many` for languages that need them, e.g. Arabic/Russian)
and pass `{ count }`. English requires both `_one` and `_other` (enforced by `i18n:check` and tests).

### Dates, numbers
`utils/dateFormat.ts` follows the active language's `intlLocale` (month names localise) and always stays in IST.
Digits stay Latin and money keeps Indian grouping in every language — a deliberate choice for an accounting-style app.

## Tooling

| Command | Purpose |
|---|---|
| `npm run i18n:check` | CI gate (already in `.github/workflows/ci.yml`): errors on stray keys/placeholder/tag mismatches |
| `npm run i18n:check -- --unused` | also lists keys no code references |
| `npm run i18n:audit` (`-- --verbose`) | lists user-visible JSX text still hardcoded in English |
| `npm run i18n:sync` | regenerate `locales/*/index.ts` after adding/removing a namespace file |

Adding a namespace = create `locales/en/<ns>.json` (+ the same file per language) and run `i18n:sync`.

## SEO — what is and isn't done
* `<html lang>` and `dir` follow the language; `og:locale` / `og:locale:alternate` are emitted by `<SEO>`.
* All languages are served from **one URL** (chosen client-side, stored in `localStorage["language"]`),
  and the prerendered snapshots used for crawlers are **English**. So `hreflang` is intentionally **not** emitted
  (it requires a distinct URL per language) and Hindi text is not indexed separately.
* **Upgrade path if Hindi search traffic matters:** serve `/hi/...` routes, prerender them with
  `localStorage.language="hi"`, add them to `sitemap.xml`, and emit `<link rel="alternate" hreflang>` in `<SEO>`.

## Known limits
* **Server-generated text stays English**: API error messages, notification titles/bodies and emails.
  The frontend already sends `Accept-Language` on every API call so the backend can localise later.
* PDF/CSV **exports stay English** (headers, titles): the bundled PDF fonts cannot render Devanagari and CSVs are
  consumed by other tools.
* Legal pages (`PrivacyPolicy`, `TermsOfService`, `RefundPolicy`) and the **admin panel** are not yet translated
  (`npm run i18n:audit` shows exactly what remains). Translate legal text with legal review.
* Insurance-company/product proper nouns, plan names (Starter, Basic…), brand name and acronyms (EMI, SIP, FD, IFSC, UPI…)
  are intentionally left in English.
